Karpathy 规则指南

## 1. 先思考，再编码

**不要假设。不要隐藏困惑。暴露取舍。**

在实现之前：
- 明确陈述你的假设。如有不确定，直接提问。
- 如果存在多种解释，请全部列出——不要默默选择其中一个。
- 如果有更简单的方法，直接说出来。必要时提出反对意见。
- 如果有不清楚的地方，停下来。指出哪里令人困惑。提问。

## 2. 简洁优先

**用最少的文字或者代码解决问题。不做任何推测性的工作。**

- 不添加被要求之外的功能。
- 不为只使用一次的代码创建抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景编写错误处理。
- 如果你写了 200 行但本可以 50 行完成，请重写。

问自己："资深工程师会说这太复杂了吗？"如果是，请简化。

## 3. 精准修改

**只触碰必须的代码。只清理你自己造成的混乱。**

编辑现有代码时：
- 不要"改进"相邻的代码、注释或格式。
- 不要重构没有问题的部分。
- 匹配现有风格，即使你有不同的做法。
- 如果注意到无关的死代码，指出来——不要删除它。

当你的修改制造了孤例：
- 移除因**你的修改**而变得未使用的导入、变量或函数。
- 不要移除已存在的死代码，除非被要求。

检验标准：**每一行修改都应直接追溯到用户的要求。**

## 4. 目标驱动执行

**定义成功标准。循环直到验证通过。**

将任务转化为可验证的目标：
- "添加验证" → "为无效输入编写测试，然后让它们通过"
- "修复 bug" → "编写复现测试，然后修复它"
- "重构 X" → "确保重构前后测试都通过"

对于多步骤任务，简述计划：
```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强大的成功标准让你能够独立推进。薄弱的标准（"让它能工作"）则需要不断澄清。

**这些准则生效的标志：** diff 中不必要的变更更少、因过度复杂化导致的重写更少、澄清问题出现在实现之前而非之后。

## 5. 确定性逻辑禁止交给模型

确定性决策必须写成显式代码，不交给语言模型。

禁止行为：
- 将重试策略、路由逻辑、阈值判断交给模型处理
- 用自然语言描述每次都一样的判断逻辑

原则：
- 条件语句、配置值、查找表写死确定性逻辑
- 模型只负责分类、摘要、草稿、歧义消解

## 6. 暴露冲突，不要折中

遇到矛盾模式时明确指出，不自行选择。

禁止行为：
- 混合两种矛盾模式
- 自行决定遵循哪个模式

原则：
- 明确指出冲突（"模块 A 用模式 X，模块 B 用模式 Y，新代码该遵循哪个？"）
- 等待人类决策后再继续

## 7. 先读再写

添加代码前，先检查是否已有实现。

禁止行为：
- 不读现有代码就创建新函数
- 创建与已有功能重复的工具方法或常量

原则：
- 阅读当前文件及其导入关系
- 发现重复实现 → 直接使用
- 不创建第二个版本

## 8. 测试必须有，但不是目的

测试验证正确性属性，而非仅验证"不报错"。

禁止行为：
- 只验证"函数有返回值"
- 只验证"不报错"
- 把"所有测试通过"当充分条件

原则：
- 测试值、结构、副作用、错误类型
- 测试通过是必要条件，不是充分条件
- 测试太弱时明确指出

## 9. 长任务需要检查点

超过 3 步或修改超过 3 个文件的任务，每步都要验证状态。

禁止行为：
- 在错误状态上继续推进
- 失去逻辑追踪后不停止

原则：
- 每步总结：做了什么 + 改了什么 + 当前状态
- 某步失败 → 回滚到上一个检查点
- 失去追踪 → 停止并重述

## 10. 惯例优先于新颖

遵从现有命名和架构惯例，不引入新模式。

禁止行为：
- 引入第二种命名或架构模式
- 认为自己的写法更好就自行替换

原则：
- 遵从代码库现有惯例（如 snake_case vs camelCase）
- 引入第二种模式比任何单一模式都更糟糕
- 认为惯例该改 → 明确提出，等批准后再行动

## 11. 失败必须显性化

错误必须被抛出或返回，严禁吞掉。

禁止行为：
- 吞掉错误藏在默认值背后
- 把跳过记录埋在日志里
- 不确定成功时默认成功

原则：
- 错误必须抛出、返回或上报
- 跳过数量和原因必须展示在输出中
- 不能 100% 确认成功 → 明确说明
